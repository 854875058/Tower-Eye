## 一、系统介绍（开场 3-5 分钟）

### 1.1 一句话定位

> "这是一套面向铁塔告警场景的**多模态智能检索与分析平台**，把结构化数据（告警工单、设备信息）和非结构化数据（现场图片、视频）打通，让运维人员用**自然语言、图片、甚至视频片段**就能快速定位历史告警、分析趋势、辅助决策。"

### 1.2 解决什么问题

| 传统痛点 | 我们的方案 |
|---------|----------|
| 告警图片/视频散落在文件服务器，查找靠人工翻目录 | 向量化索引 + 多模态检索，文字描述或拖入图片即可秒级召回 |
| 结构化工单和非结构化图片是两套系统，无法联合查询 | LanceDB 统一数据底座 + DuckDB SQL 引擎，一次查询同时过滤结构化字段 + 向量相似度排序 |
| 统计分析靠导出 Excel 手动做 | 自然语言问答（NL2SQL），直接问"上个月福州车辆闯入告警有多少条"就出结果 |
| 新增筛选维度要改代码重建索引 | 架构解耦——结构化过滤走 DuckDB，新增字段只改前端，不用重跑向量嵌入 |
| 告警图片缺少语义标签 | Qwen3-VL 视觉语言模型自动分析图片内容，生成中文场景描述 |

### 1.3 技术架构概览（配合系统"架构总览"页面讲）

**关键模型清单**（演示时可以提一下）：
- **Qwen3-VL**：阿里通义千问视觉语言模型，负责图像向量化（Embedding）、相关性精排（Reranker）、图像内容理解
- **DeepSeek Chat**：负责自然语言转 SQL（NL2SQL）

### 第二幕：智能问答 — 双路融合检索（8-10 分钟）⭐ 重点

这是最能体现"结构化 + 非结构化融合"的环节，建议多花时间。

**底层原理（讲给领导听）**：

> 智能问答不是简单的 NL2SQL，而是一个**双路融合检索系统**。用户用自然语言提问后，系统同时走两条路：
>
> **第一条路（结构化路径）**：用 DeepSeek 大模型把自然语言翻译成 SQL，在 DuckDB 中精确查询告警工单的结构化字段（事件类型、时间、地址、设备等）。这条路保证**精确性**——用户问"车辆闯入告警"，就一定只返回 event_type='车辆闯入监控告警' 的记录。
>
> **第二条路（语义路径）**：同时用 Qwen3-VL 把用户问题编码成向量，在 LanceDB 中做向量检索，找到**图片内容**与问题语义最相关的记录。这条路保证**语义理解**——不仅看工单字段，还看图片里实际拍到了什么。
>
> 两条路的结果通过图片文件名做交叉匹配：
> - **交集**（SQL 命中 + 向量也命中）：说明这条记录既满足结构化条件，图片内容也跟问题相关，会标注语义匹配分数
> - **向量独有**（SQL 没命中但向量命中）：说明图片内容跟问题相关但不在结构化筛选范围内，作为"您可能还感兴趣"推荐给用户
>
> 这就是真正的**多模态融合**——不是两个系统各查各的，而是一次查询同时利用结构化数据和图片语义。

**完整技术链路**（可以配合"思考过程"折叠面板讲）：

```
用户提问 "查询最近20条车辆闯入告警"
    │
    ▼
① 意图识别（规则引擎）
    → intent=list, event_type=车辆闯入监控告警, top_k=20
    │
    ▼
② SQL 缓存查找
    → 问题归一化（去掉具体数字/日期）→ MD5 哈希 → 查 traces.db
    → 命中：复用历史 SQL 模板，params 实时重新提取
    → 未命中：调 DeepSeek LLM 生成 SQL
    │
    ▼
③ SQL 安全校验（Guardrail）
    → 只允许 SELECT，禁止 DROP/DELETE/UPDATE
    → 表名白名单检查，参数清理
    │
    ▼
④ DuckDB 执行 SQL
    → SELECT * FROM events WHERE event_type='车辆闯入监控告警'
      ORDER BY alarm_time DESC LIMIT 20
    → 返回 20 条结构化记录（含所有字段）
    │
    ▼
⑤ 语义增强（双路融合）  ← 这是核心创新点
    → Qwen3-VL 把 "车辆闯入告警" 编码成 4096 维向量
    → LanceDB hybrid_search：向量相似度(0.7) + summary关键词匹配(0.3)
    → 通过 file_path 匹配 SQL 结果，附加语义分数
    → 向量检索独有结果 → "您可能还感兴趣"推荐
    │
    ▼
⑥ 结果展示
    → 表格（默认隐藏路径等长字段，可展开）
    → 媒体预览（原图 / 标注框图 / 视频 tabs）
    → 每条详情标题显示 [语义 85%] 分数
    → VL 图像理解摘要（"画面中一辆白色货车停在铁塔基站围栏外..."）
    → "您可能还感兴趣" 推荐区
```

**演示步骤**：

#### 场景 1：简单统计查询
1. 在问答框输入：**"统计各类告警数量"**

4. **讲解**："用户不需要懂 SQL，用自然语言就能做数据分析。系统自动识别'统计'意图，生成 GROUP BY 查询"

#### 场景 2：带条件的列表查询 + 双路融合
1. 输入：**"查询最近20条车辆闯入告警的详细信息"**
2. 系统返回结果后，注意看几个关键展示：
   - 标题栏的紫色 **"语义匹配 15/20"** 徽章 → 说明 20 条 SQL 结果中有 15 条在向量检索中也被命中

3. **讲解**："这就是双路融合的效果——SQL 保证了结构化条件的精确匹配，向量检索补充了图片内容的语义理解。每条记录不仅有工单字段，还有 AI 对图片内容的理解描述，以及语义匹配度评分"

#### 场景 3：展示自纠错能力
1. 输入一个稍微复杂的问题，比如：**"按街道统计最近30天各类告警数量"**

4. **讲解**："我们实现了 LLM 自纠错机制——如果生成的 SQL 执行失败，系统会把错误信息反馈给大模型，让它修正 SQL 再重试，最多 3 轮。同时系统有 SQL 缓存池，成功的查询会被缓存，下次类似问题直接复用，响应从秒级降到毫秒级"

#### 场景 4：SQL 安全防护
1. 可以口头提一下（不一定要演示）
2. **讲解**："所有生成的 SQL 都经过安全校验——只允许 SELECT，禁止 DROP/DELETE/UPDATE 等危险操作，防止 LLM 幻觉导致数据被破坏"

### 第三幕：多模态检索（8-10 分钟）⭐⭐ 最大亮点

**底层原理（讲给领导听）**：

> 多模态检索的核心是**跨模态语义对齐**——用 Qwen3-VL 视觉语言模型把文字、图片、视频统一映射到同一个 4096 维的向量空间。在这个空间里，语义相近的内容（不管是文字还是图片）距离就近。
>
> 具体来说：
> - **数据入库时**：每张告警图片经过 Qwen3-VL 编码成一个 4096 维向量，连同结构化元数据（事件类型、时间、地址等 30+ 字段）一起存入 LanceDB。同时 Qwen3-VL 还会对图片做场景理解，生成中文摘要（"画面中一辆白色货车停在铁塔基站围栏外，天气晴朗，远处有施工围挡"），也存入数据库。
> - **检索时**：用户输入的文字/上传的图片同样经过 Qwen3-VL 编码成向量，然后在 LanceDB 中做近似最近邻搜索（ANN），找到向量距离最近的图片。
> - **混合检索**：不是纯向量检索，而是 **向量相似度(70%) + 关键词匹配(30%)** 的混合打分。关键词匹配是拿用户查询文本和图片的 VL 摘要做分词匹配，这样即使向量距离差不多，包含关键词的结果也会排更前面。
> - **二阶段精排**：粗排拿到 top-50 候选后，再用 Qwen3-VL Reranker 模型做精细打分（Cross-encoder 架构，同时看 query 和 candidate），最终返回 top-10。
>
> 整个检索还支持**结构化预过滤**——用户可以在高级筛选面板选择城市、告警类型等条件，系统先用 DuckDB 筛出符合条件的 asset_id 集合，再在这个子集上做向量检索。这样既保证了结构化条件的精确性，又利用了向量检索的语义能力。

**完整技术链路**：

```
用户输入 "挖掘机在工地作业"
    │
    ▼
① 输入分流
    → 纯文本 → Qwen3-VL 文本编码 → 4096维向量
    → 图片   → Qwen3-VL 图像编码 → 4096维向量
    → 视频   → OpenCV 抽中间帧 → 图像编码 → 4096维向量
    │
    ▼
② 结构化预过滤（如果有筛选条件）
    → DuckDB: SELECT DISTINCT asset_id FROM events WHERE city_name='福州'
    → 得到 asset_id 白名单 → 注入 LanceDB WHERE 子句
    │
    ▼
③ LanceDB 向量检索（粗排）
    → ANN 搜索 top-50 候选
    → 混合打分: 0.7×向量余弦相似度 + 0.3×summary关键词匹配
    │
    ▼
④ Reranker 精排（可选）
    → Qwen3-VL Reranker 对 top-50 逐条计算精细相关性
    → 最终分数 = 0.7×Reranker + 0.3×原始向量分
    │
    ▼
⑤ 结果展示
    → 图片卡片网格（缩略图 + 相似度分数 + 事件类型标签）
    → 点击展开详情：原图/标注框图/视频 tabs + 全部结构化字段
    → 关联数据：同一告警事件的多张图片和视频
```

## 三、核心技术亮点讲解

### 3.1 向量检索原理（甲方如果问"怎么做到文搜图的"）

**简洁版**（给非技术领导）：
> "我们用 Qwen3-VL 视觉语言模型把每张图片转换成一个高维向量（可以理解为图片的'数字指纹'），同时把用户输入的文字也转换成同一空间的向量。然后计算两个向量的余弦相似度，相似度越高说明语义越接近。"

**技术版**（给懂算法的人）：
> "我们使用 Qwen3-VL 作为多模态 Embedding 模型，它是一个 Vision-Language 预训练模型，在大规模图文对上做了对比学习（Contrastive Learning），使得文本和图像被映射到同一个语义空间。具体来说：
> - 图像通过 ViT（Vision Transformer）编码为视觉 token
> - 文本通过 LLM 的 tokenizer + transformer 编码为文本 token
> - 两者经过投影层映射到同一维度空间，做 L2 归一化
> - 检索时计算余弦相似度（cosine similarity），用 LanceDB 做 ANN（近似最近邻）加速
>
> 相比传统 CLIP，Qwen3-VL 的优势是中文理解能力更强，对中国场景（工地、铁塔、告警场景）的识别更准确。"

### 3.2 两阶段检索（Embedding + Reranker）

> "我们采用业界标准的两阶段检索架构：
> - **第一阶段（召回）**：Qwen3-VL Embedding 模型做向量检索，从几百张图片中快速召回 top-K 候选（毫秒级）
> - **第二阶段（精排）**：Qwen3-VL Reranker 模型对候选结果逐一计算精细相关性分数，重新排序
>
> Reranker 的精度比 Embedding 高，但速度慢（需要逐条计算），所以只对第一阶段的候选做精排。最终分数 = 0.7 × Reranker 相关性 + 0.3 × 原始向量相似度。"

### 3.3 NL2SQL 技术方案

> "自然语言转 SQL 采用**混合模式**：
> - **主路径**：调用 DeepSeek 大模型，把用户问题 + 数据库 Schema（自动从 DuckDB 读取表结构和样例值）+ 当前时间一起发给 LLM，让它生成 SQL
> - **备用路径**：如果 LLM 调用失败或超时，降级到规则引擎（正则匹配 + 关键词映射 + 实体提取）
> - **SQL 缓存池**：成功执行的查询会被缓存（问题归一化 → MD5 哈希），下次类似问题直接复用 SQL 模板，响应从秒级降到毫秒级
> - **自纠错**：如果生成的 SQL 执行报错，把错误信息反馈给 LLM 重新生成，最多重试 3 次
> - **安全防护**：SQL Guardrail 层只允许 SELECT，禁止所有写操作和危险语句
> - **当前时间注入**：每次调用 LLM 都注入 `datetime.now()`，解决 LLM 不知道'现在'是什么时候的问题"

### 3.4 双路融合架构（核心创新点）

> "这是我们架构设计的**核心创新点**——真正实现了结构化数据和非结构化数据的融合检索：
>
> **数据层**：
> - **LanceDB**（向量数据库）：存储图片向量（4096维）+ 全部结构化元数据（30+ 字段）+ VL 图像理解摘要，是统一数据底座
> - **DuckDB**（SQL 引擎）：直接读取 LanceDB 的 Lance 表做 SQL 分析，不需要数据同步
> - 一份数据，两种查询方式：向量检索走 LanceDB ANN，结构化查询走 DuckDB SQL
>
> **查询层（双路融合）**：
> - 用户提问后，**第一条路**走 NL2SQL → DuckDB 精确查询结构化字段
> - **第二条路**同时走 Qwen3-VL 编码 → LanceDB 向量检索，找图片内容语义相关的记录
> - 两路结果通过 file_path 做交叉匹配：交集附加语义分数，向量独有结果作为推荐
>
> **展示层**：
> - 每条记录标注语义匹配度（如 [语义 85%]）
> - 详情页展示 VL 图像理解摘要（AI 对图片内容的中文描述）
> - "您可能还感兴趣"区域展示向量检索发现的额外相关图片
>
> 这样设计的好处：
> 1. SQL 保底——即使向量检索不可用，结构化查询依然正常工作
> 2. 语义增值——向量检索补充了图片内容维度的信息，不再只是查工单字段
> 3. 新增字段只需要改 DuckDB 查询，**不需要重新生成向量嵌入**"

### 3.5 自动标注技术

> "自动标注采用 YOLO + VL 双引擎：
> - **YOLOv8x-WorldV2**：开放词汇目标检测模型，能检测预定义的 12 类目标（人、车、挖掘机等），输出边界框和置信度
> - **Qwen3-VL**：视觉语言模型，负责场景级理解——描述图片中发生了什么、有哪些物体、天气光照条件等
> - **视频跟踪**：YOLOv8x 逐帧检测 + Kalman 滤波器做状态预测 + IoU（交并比）做帧间关联，实现多目标跟踪"

## 四、甲方可能提问 & 应答策略

### Q1："向量检索的准确率怎么样？有没有量化指标？"

**现状回答**：
> "目前是 POC 阶段，我们在铁塔告警数据集上做了定性验证——文搜图和以图搜图的 top-10 召回结果人工评估准确率在 80% 以上。加上 Reranker 精排后，top-5 的准确率能进一步提升。"

**后续规划**：
> "正式项目中我们会建立标准评测集，用 Recall@K、MRR（Mean Reciprocal Rank）、NDCG 等指标做量化评估。同时会针对铁塔场景做 fine-tune，进一步提升准确率。"

### Q2："Qwen3-VL 模型是部署在哪里的？推理性能怎么样？"

**回答**：
> "目前 Qwen3-VL 部署在内网 GPU 服务器上（10.132.19.82），通过 HTTP API 调用。Embedding 接口单张图片响应时间在 100-300ms，Reranker 单条在 200-500ms。
>
> 生产环境可以考虑：
> - 用 vLLM 或 TensorRT-LLM 做推理加速
> - 多卡部署做负载均衡
> - Embedding 结果做缓存，同一张图不重复计算"

### Q3："数据量大了以后性能怎么样？能支持多大规模？"

**回答**：
> "当前 POC 数据量是几百条，LanceDB 本身支持百万级向量的毫秒级检索（基于 IVF-PQ 索引）。DuckDB 是列式分析引擎，在百万级数据量下也能保持良好性能。
>
> 如果数据量到千万级，我们的扩展路径是：
> - DuckDB → PostgreSQL（或 ClickHouse）
> - LanceDB → Milvus 或 Qdrant（分布式向量数据库）
> - 加入 Redis 缓存热点查询
> - Embedding 计算走离线批处理 + 增量更新"

### Q4："NL2SQL 的准确率怎么样？复杂查询能处理吗？"

**回答**：
> "简单查询（统计、列表、时间过滤）准确率很高，基本一次就对。复杂查询（多表关联、嵌套子查询）可能需要 1-2 次自纠错。我们的设计是：
> - LLM 生成 SQL 时，会把完整的表结构、字段说明、样例值都传给模型，减少幻觉
> - 自纠错机制保证即使第一次错了也能自动修复
> - 规则引擎兜底，确保基本查询不依赖 LLM 也能工作
>
> 后续可以通过 few-shot 示例库（积累常见问题的标准 SQL）进一步提升准确率。"

### Q5："模型是在线调用还是本地部署？对网络有什么要求？"

**回答**：
> "目前的部署方式：
> - **Qwen3-VL**（Embedding + Reranker + VL 分析）：部署在内网 GPU 服务器，HTTP API 调用，不依赖外网
> - **DeepSeek**（NL2SQL）：调用 DeepSeek 云端 API，需要外网访问
>
> 生产环境可以全部本地化部署：
> - DeepSeek 可以换成本地部署的开源 LLM（如 Qwen2.5-72B、DeepSeek-V3 本地版）
> - 所有模型都可以在客户内网 GPU 服务器上运行，完全离线，数据不出网"

### Q6："跟市面上的 RAG 方案有什么区别？"

**回答**：
> "传统 RAG 主要处理文本文档（PDF、Word），我们的方案是**多模态 RAG**：
> - 不仅检索文本，还能检索图片和视频
> - 不仅做文本相似度，还做视觉相似度
> - 结合了结构化数据（工单字段）和非结构化数据（图片向量），是真正的'融合检索'
> - **双路融合**：智能问答同时走 SQL 精确查询 + 向量语义检索，两路结果交叉匹配
>
> 另外我们不是简单的'检索+生成'，而是'检索+分析'——NL2SQL 直接查数据库做精确统计，不存在 LLM 幻觉导致数字不准的问题。向量检索作为补充，提供图片内容维度的语义理解。"

### Q7："自动标注的精度怎么样？能替代人工吗？"

**回答**：
> "YOLOv8x-WorldV2 在通用目标检测上精度很高（COCO mAP 50+），但在铁塔特定场景（如区分挖掘机和装载机）可能需要微调。
>
> 我们的定位是**辅助标注**而非完全替代人工：
> - 模型先自动标注，人工只需要审核和修正
> - 可以把人工修正的结果反馈回去做增量训练
> - 预计能减少 60-80% 的人工标注工作量"

### Q8："数据安全怎么保证？SQL 注入怎么防？"

**回答**：
> "我们有多层安全防护：
> 1. **SQL Guardrail**：所有 LLM 生成的 SQL 都经过白名单校验，只允许 SELECT，禁止 DROP/DELETE/UPDATE 等写操作
> 2. **参数化查询**：DuckDB 查询全部使用参数化（`?` 占位符），防止 SQL 注入
> 3. **表名白名单**：只允许访问配置中声明的表，敏感表被屏蔽
> 4. **注释过滤**：SQL 中的注释符号（`--`、`/*`、`#`）会被过滤，防止注释注入攻击
> 5. **数据不出网**：所有数据存储和处理都在内网完成"

### Q9："这个系统能不能对接我们现有的告警平台？"

**回答**：
> "完全可以。我们的数据入库支持多种格式：
> - CSV、JSON 文件批量导入
> - 数据库字段映射可配置（通过 `extra_json` 存储原始字段，兼容任意 schema）
> - 后续可以开发 API 接口做实时对接，新告警产生时自动入库 + 生成向量
>
> 架构上我们已经有 FastAPI 后端，可以直接暴露 RESTful API 给外部系统调用。"

### Q10："后续的技术演进路线是什么？"

**回答**：
> "我们规划了三个阶段：
>
> **近期（1-2 个月）**：
> - 针对铁塔场景微调 Embedding 模型，提升检索准确率
> - 积累 NL2SQL few-shot 示例库，提升复杂查询成功率
> - 增量更新机制——新告警自动入库 + 自动生成向量，不用全量重跑
>
> **中期（3-6 个月）**：
> - 接入实时告警流（Kafka/RabbitMQ），实现准实时检索
> - 多模态 RAG 增强——检索到图片后，用 VL 模型生成自然语言分析报告
> - 视频片段检索（不只是单帧，而是视频语义理解）
>
> **远期**：
> - 分布式部署，支持千万级数据
> - 告警趋势预测（时序分析 + 异常检测）
> - 跨模态知识图谱——设备、地点、事件、图片之间的关联推理"

## 六、关键术语速查（演示时可能用到）

| 术语 | 通俗解释 | 技术解释 |
|------|---------|---------|
| 向量嵌入 (Embedding) | 把图片/文字转成一串数字 | 通过预训练模型将输入映射到高维向量空间 |
| 余弦相似度 (Cosine Similarity) | 两个向量的"方向"有多接近 | cos(θ) = A·B / (‖A‖·‖B‖)，值域 [-1, 1] |
| ANN (近似最近邻) | 快速找到最相似的向量 | IVF-PQ 索引，牺牲少量精度换取数量级的速度提升 |
| Reranker (精排器) | 对粗排结果做精细打分 | Cross-encoder 架构，同时看 query 和 candidate 做交叉注意力 |
| NL2SQL | 自然语言转数据库查询 | LLM + Schema Prompt + 自纠错循环 |
| VL 模型 | 能同时理解图片和文字的 AI | Vision-Language Model，如 Qwen3-VL |
| Kalman 滤波 | 预测目标下一帧位置 | 线性状态空间模型，6 维状态 (cx, cy, w, h, vx, vy) |
| IoU (交并比) | 两个框重叠程度 | Intersection over Union，用于目标跟踪的帧间关联 |
| LanceDB | 轻量级向量数据库 | 基于 Apache Arrow 的嵌入式向量数据库，支持 SQL-like 过滤 |
| Contrastive Learning | 让相似的靠近、不相似的远离 | 对比学习，CLIP/Qwen3-VL 的核心训练方法 |
